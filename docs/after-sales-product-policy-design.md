# 售后商品身份、兼容关系与补发规则设计建议

状态：研究与设计提案，尚未实现；不代表当前生产行为。

调研与代码核对日期：2026-10-26（北京时间）。适用工作树：5186 / `codex/mabang-catalog-rma`。

本次仅新增设计文档，不修改商品配置、质保政策、RMA 或马邦数据。此前受控开放的三个 SKU 见 [配置记录](controlled-reship-policy.md)。本文示例中的阈值和关系需要业务及产品负责人确认，不自动生效。

## 1. 结论与设计目标

`allowReship` 适合作为一个商品能否进入补发候选的总开关，但不能表达“针对什么原商品、何种故障、什么地区、补多少、谁付费、由谁批准、如何履约”。补发应根据一次明确的售后诉求计算结果，至少分开回答：

1. 原单卖的究竟是什么商品或套装？
2. 候选件是否适合受影响的设备、版本和市场？
3. 此次诉求是否有免费补发权益，还是需要付费或善意例外审批？
4. 该请求是否超过数量、次数或已授权未履行额度？
5. 实际履约商品、库存、仓库与批次是否可用？

这五个问题分别需要商品身份、技术关系、售后政策、额度记账和履约能力。保持模块化单体即可，先建立契约和数据所有权，不需要先拆微服务或引入通用规则引擎。

## 2. 本地发现：已确认事实与风险

| 已核对事实 | 潜在业务问题 | 建议 |
| --- | --- | --- |
| 当前目录有 104 个 SKU；包括地区型号、翻新机、套装、赠品、待匹配项、差价项、风嘴和 ColorBox 染剂 | 所有对象仅用 general/device/part 分类不足 | 增加商品族、具体变体、实物角色、成色及服务属性 |
| 三个已开启补发的 SKU 都是 `deviceIds=[]` | `validateProduct` 只有列表非空时才限制设备，空列表相当于无兼容限制 | 将未配置、明确通用、指定兼容范围区分开 |
| 整机补发检查类型及开关，没有原型号到补发型号的市场、电气和版本规则 | 美国版与其他地区版可能同时可选；类型相同不等于可替换 | 建立受控的原变体到目标变体的替代关系 |
| `Match` 按 SKU 或 aliases 在商品集合中识别；当前样本未发现别名冲突 | 当前没有显式的平台/店铺/生效期作用域，未来重用编码或同号会有歧义 | 外部身份映射有作用域、版本及唯一性约束 |
| 马邦 masterSku/aliases 被保留 | 源主 SKU、别名不必然代表同一实物，也不代表兼容或可替代 | 先作为外部证据，审核后形成 CRM 身份或关系 |
| 已有套装及赠品 SKU | 购买套装不必然需要整套补发；源订单也可能已经拆出组件行 | 保存购买时的组成快照及展开方式，避免双计数 |
| 补发数量目前主要是 1–1,000,000 的通用整数校验，限制一张单内重复 SKU | 缺少针对订单行/设备/事故的业务额度，跨工单可重复申请 | 业务数量规则 + 原子授权额度台账 |
| 草稿重复提交保护和同工单关联 RMA 提示已存在 | 不等于同一原订单行跨工单、跨客服的防重复补发 | 以稳定的原商品/资产和诉求为范围做重复检测 |
| 当前补发开关在创建与执行时重查，但市场、技术关系尚未配置 | 创建时选中商品，执行时可能已被停用或召回 | 保存决定依据，执行时重查当前硬性限制 |
| 当前质保模板含 device 12 个月、两种打印头类别及宽限期；三个受控 SKU 仍为 none | 通用旧模板不等于已批准的 Zuvi 全产品政策 | 按商品族/地区/购买方式发布适用政策；不要自动给新产品套用旧期限 |
| 马邦连接只允许四个只读 API；没有补发下单、库存预占或发货能力 | CRM 中“记录发出”不能证明外部已发货，库存快照不能保证有货 | 明确当前履约模式为人工，未来验证写接口后才接自动履约 |

主要代码依据：`backend/internal/catalog/service.go` 的导入、策略保存和名称提示；`backend/internal/originalorders/service.go` 的 Match/Confirm/Bind；`backend/internal/support/support.go` 的 rma.create、values、validateProduct 和 rmatask.execute；`backend/internal/support/warranty.go`；`frontend/src/support.jsx` 的 ReshipLines。

这些是当前实现的边界和缺口，不是已经发生了错发、欺诈或安全事故的声明。SKU 后缀与名称只能提出需要核对的属性，不作为电压、认证或技术兼容的证据。

## 3. 其他系统的可借鉴做法与边界

| 官方资料 | 文档明确支持的概念 | 我们借鉴的方式 |
| --- | --- | --- |
| Microsoft Dynamics 产品标识 [S1] | 稳定产品编号、变体及维度、外部客户/供应商编号；名称不要求唯一 | 稳定 CRM 变体 ID 与外部 SKU 编号分开 |
| Oracle Service Logistics [S2] | 替代件和后继型号分别配置；直接替代与后继链采用不同查找方式 | 分开建关系，不通过字符串相似度或一张 alias 表推导 |
| Dynamics Field Service 客户资产 [S3] | 产品与客户持有资产分开；资产可有父子组件和服务历史 | 目录型号与客户实际设备分开，后续维护换机链及组件历史 |
| Odoo Kits [S4] | 套装由 BoM 定义；销售单可显示套装行，交付按组件列出 | 保留订单时套装组成，售后针对受影响组件做决策 |
| Odoo Repairs [S5] | 被维修产品、序列号、添加/移除/回收零件、保内与收费处理 | 把故障对象、使用零件、费用归属分开 |
| Odoo Expiration dates [S6] | 通过批次或序列号管理效期 | 耗材 SKU 与实际批次分开，批次效期在出库时校验 |
| Dynamics Sales returns [S7] | 退回原因与收货后处置分开；退货与替换销售单有关联但独立 | 申请、退回处理、补发履约分开；保留关联 |
| Dynamics 工单权益 [S8] | 权益可按条件提供价格表、折扣或免费产品/服务 | 技术兼容与免费服务资格分开，不用一个保内勾选框代替完整政策 |

特别注意：S7 中的某种 replacement-by-disposition 流程明确“不验证或限制替换商品身份与数量”。因此，不能把“成熟 ERP 支持换货”理解为系统天然会阻止错型号和超量补发。我们需要自己定义这些约束。

## 4. 基础模型：先把几种不同的 mapping 分清

### 4.1 产品族、型号变体、外部商品和客户资产

建议先在现有 catalog 内增加稳定的内部实体，不要求一次推倒现有 products：

| 对象 | 回答的问题 | 核心数据 |
| --- | --- | --- |
| ProductFamily | 属于哪一产品系列？ | 稳定 ID、名称；例如 Halo、后续某产品系列 |
| ProductVariant | 是哪一种可区分的实物？ | 内部 ID、产品族、型号、硬件版本、市场、电气/接口规格、容量或颜色等适用维度 |
| ExternalItemBinding | 外部哪条商品记录对应它？ | connectionId、租户、外部 itemId、源 SKU、角色、目标变体 ID、有效期、证据与审核状态 |
| ChannelIdentity | 某店铺原单里的编号是什么？ | 平台/店铺作用域、源商品/变体编号或卖家 SKU、有效期、目标绑定 |
| CustomerAsset | 客户实际持有哪台设备？ | 资产 ID、原订单行、变体、SN（有则保存）、版本证据、售后历史、换机链 |

旧订单没有 SN 时可先用已确认订单行及受影响数量定位，不强制虚构序列号。关系计算需要版本但暂缺版本时返回“待补信息”；SN 后续补录要有证据和审计。

同一实物可能有多个销售编码；但不能因为名字近似、SKU 有相同前缀或 masterSku 相同，就自动合并。反过来，套装和整机不能映射为同一个可履约变体。

身份映射在相同作用域及重叠有效期内必须唯一；遇到多候选明确待确认，不取第一条。停用旧编码不删除历史映射。大小写是否等价由来源契约决定，不全局强制转换并改写源值。

### 4.2 商品类别与独立属性

最小类型：`device` 整机、`accessory` 可独立补发配件、`consumable` 耗材、`kit` 套装、`non_physical` 非实物。待分类是配置状态，不是已经确认的实物类型。

独立属性：

- 成色：新品/翻新/其他已批准状态，与角色类型分开。
- 生命周期：开发、可销售、仅售后、停用、召回/禁止履约；源状态与 CRM 服务状态分开。
- 单位：个、瓶、盒等及明确换算；不用浮点数做数量/容量结算。
- 是否要求 SN、批次、效期；先允许未采集，相关动作前要求补齐。
- 销售与服务用途分别授权。停售商品仍可识别，专用售后备件即使不可销售也可在批准后补发。

当前 `reshipCandidate` 来自源在售状态和名称排除提示，只能作为待审核提示，不应提升成最终规则。差价、邮费、维修服务、测试项要显式标为非实物，不能长期依赖名称黑名单。

### 4.3 三种关系必须独立

1. **身份映射**：外部编号表示哪个 CRM 商品。它不授予补发许可。
2. **兼容关系 CompatibleWith**：某零件/耗材是否能用于某设备变体及硬件版本。
3. **替代关系 Replaces/Supersedes**：某目标变体能否替换原变体；可以附带地区、成色、故障、客户同意、审批和转换数量条件。

套装组成 KitComponent 是第四种结构关系，也不自动构成技术兼容和免费权益。

关系表应包含：作用域、方向、来源证据、审核人、生效/失效时间、版本、必要技术条件。替代关系 A→B 不意味着 B→A，也不自动意味着 A→C。第一期只支持审核过的直接关系；后续即使支持后继链，也要检查循环并重新检查最终目标的全部限制。

## 5. 规则应该在哪些层定义

### 5.1 技术及履约硬限制

| 范围 | 最低规则 | 未知/不匹配时 |
| --- | --- | --- |
| 地区整机 | 原机规格 + 接收地 + 目标机市场/电气规格的明确组合 | 缺信息则待补；已知不兼容则禁止 |
| 配件 | 兼容模式：待配置 / 指定型号及版本 / 明确通用（仍限定产品族等范围） | 空列表不能表示通用 |
| 耗材 | 产品族/设备接口、配方代际、颜色/规格、单位换算 | 不能仅因“都是染剂”互换 |
| 成色替代 | 新品→翻新、升级型号、不同颜色等具有独立政策及客户确认要求 | 不自动选更便宜或库存更多的型号 |
| 套装 | 购买时组成、受影响组件、源单是否已拆件 | 不能假设拆件完整，也不能双计数 |
| 质量状态 | 召回、停发、批次冻结、过期 | 硬性禁止，不由金额审批绕过 |
| 来源与履约 | 有有效的目标系统商品绑定且允许该履约路线 | 无映射不猜一个 ERP SKU 提交 |

市场后缀不是电压证据；客户当前地址也不等于原购买地区。某些商品可能电气通用，需要产品负责人明确登记“适用范围”，不能默认所有型号都受同一地区限制。

### 5.2 售后权益、数量与费用归属

输入至少包括：原商品/资产、订单行及购买数量、受影响数量、问题类型、购买/交付证据、市场、政策生效日期、此前服务记录和请求明细。

- 诉求类型区分：质量故障、漏发/缺件、运输破损、耗材正常消耗、付费增购、善意补偿等。不同类型可以要求不同证据及额度。
- 保内是获得某种处理的依据，不是随便补任意 SKU 的权限。正常耗尽、错购、损坏批次不能使用同一判断。
- 单次数量、周期累计数量、金额、次数分别配置。整机按受影响设备数，缺件可按订单时套装组成，耗材按购买单位及缺损数量处理。
- 不将“原单买 1 个，所以一生只能补 1 次”写死；换机后再次故障是新的诉求，要保留资产和替换链、累计权益及例外审批依据。
- 申请量、已授权未发、已发、取消量和退回量分别记账。取消尚未履行授权可释放额度；已发货不能因取消任务就抹掉，退回也不自动恢复免费额度。
- 同一诉求并发申请须在一个事务内检查及占用服务额度。创建时的 API 幂等不能替代跨工单业务防重。
- 建议默认：确定的技术/质量禁用不可审批放行；超出免费次数/金额可走业务例外；事实缺失先补信息。例外必须有权限、原因、审批人、范围和有效期。

具体月数、次数、补偿金额、客户同意方式由业务确认，本提案不为 Halo、ColorBox 或未来产品擅自指定。

### 5.3 批次和效期属于实际出库条件

型号兼容不能证明某瓶耗材可以发货。出库时另查批次、冻结/召回、效期、最低剩余可用期及目的地限制。需要时采用先到期先出，但先满足质量和剩余有效期约束。

现有马邦契约只有商品和仓库数量快照，尚未验证批次、效期、预占和创建补发订单能力。模型可以预留字段，界面和决策必须显示“未知/待核对”，不能把未接入的数据当成已校验。第一期可采用带证据的人工批次核对，后续验证接口后接入。

## 6. 决策契约：统一后端结果，前端只负责解释

在商品和售后边界建立应用服务，例如：

```text
EvaluateReshipment(originalEvidence, affectedAsset, claim, requestedLines, destination)
  decision: allowed | approval_required | needs_information | blocked
  lines[]:
    canonicalVariantId, requestedQuantity, serviceUnit
    matchedIdentityId, compatibilityRuleId, substitutionRuleId
    reasonCodes[], missingFacts[], appliedRuleVersions[]
  entitlement: covered | chargeable | goodwill_review | unresolved
  fulfillment: manual_verification | ready | unavailable | unknown
  authorizedQuantity, expiresAt, policyVersion, factsDigest
```

这是建议契约，不是现有接口。可用库存与业务许可分别返回；“兼容且保内但库存未知”不能被描述成可立即发货。真实响应应根据字段是否适用省略无关项，并避免回传无权读取的客户资料。

页面下拉框调用同一套候选评估，显示“可补发”“需审批”“不兼容”“待补版本”等原因。RMA 创建和执行必须在后端重算，不相信前端结果，也不复制一套业务筛选规则。

无需给客服展示庞大规则卡片。默认呈现已筛选候选、适用设备和一句原因，异常时再展开所缺信息。配置端按产品族批量维护兼容和策略矩阵，SKU 页面只显示继承结果及例外。

## 7. 决策生命周期与一致性

```mermaid
flowchart LR
  A[确认原订单行与受影响设备] --> B[计算兼容候选与服务权益]
  B --> C{结果}
  C -->|缺信息| D[补证据]
  D --> B
  C -->|需审批| E[审批具体商品及数量]
  C -->|允许| F[创建 RMA 并占用服务额度]
  E --> F
  F --> G[履约前重查当前硬性限制]
  G --> H[人工履约或未来已验证的履约适配器]
  H --> I[记录实际发出及剩余授权]
```

创建时保存规则版本、事实快照和决策理由，之后不能用新目录反向改写旧单。审批过程中要占用临时额度，避免多人并发重复承诺；拒绝或超时释放。审批决定必须绑定所选 SKU、数量和关键事实摘要，修改这些信息后重新评估及必要审批。

执行时保留历史商业承诺，同时重查召回/停发、当前兼容事实、有效源绑定、数量授权等现行硬限制。规则变化导致不可执行时进入待处理，保留原承诺和变更原因，不悄悄替换商品。政策更新应声明对存量已批准单的适用方式。

额度记账与 RMA/授权状态在本地事务中一致。执行者不能绕过统一授权账本；库存预占由库存/履约系统拥有，服务额度不能冒充库存预占。未来 ERP 写入通过独立履约请求和 outbox/幂等处理；超时不等于失败，必须先查单再重试，不能重复创建外部订单。现阶段不实现或调用这些未验证的写接口。

## 8. DDD 边界与最小数据结构

| 模块 | 拥有的数据和决策 | 对外契约 |
| --- | --- | --- |
| catalog | 产品族/变体、外部身份、套装组成、技术兼容、替代关系 | ResolveProductIdentity、FindCompatibleReplacements |
| originalorders | 原单及确认事实、购买时的组件与商品识别快照 | GetConfirmedPurchase，不再由它扫描 catalog 内部集合 |
| support / aftersales | 故障诉求、服务政策、权益评估、RMA、审批及服务额度账本 | EvaluateReshipment、AuthorizeClaim、RecheckExecution |
| fulfillment / integration | 实际履约请求、外部单号、出库结果、接口幂等与重试 | QuoteAvailability、SubmitAuthorizedFulfillment；未接入时明确人工模式 |

这是现有单体内的职责划分。售后政策与技术关系可分别版本化；`allowReship` 在迁移期保留为明确总闸，不能因导入在售状态自动打开。技术关系由有权维护商品技术资料的人审核，商业权益及例外由售后负责人审批；仓库人员提供履约事实。

建议先建这些表/实体，而非一张可执行任意表达式的 rules 大表：

- catalog：product_families、product_variants、external_item_bindings、compatibility_rules、replacement_rules、kit_versions / kit_components。
- support：service_policy_versions、claim_authorizations、service_allowance_entries；现有 RMA 增加受影响订单行/组件、资产可选引用、决策快照。
- 批次、资产组件更换历史、自动履约请求在相应阶段添加，不作为首期全部建齐的前提。

可先用有类型的条件列（具体变体/产品族、版本区间、市场、原因、有效期）和显式动作，避免用户脚本或任意 SQL。先执行硬禁用，再检查技术关系和数据完整性，最后评估商业权益及例外。范围相同且同样具体的规则冲突应阻止发布；运行时若仍冲突则返回待处理，不能按创建时间随机选一条。发布前提供影响预览及规则用例。

## 9. 建议分期与验收

### 第一期：先防止错误组合

1. 104 个商品做一次受控分类，优先覆盖实际售后会用的商品；确认非实物、套装、地区和成色。保存映射来源与待确认项。
2. 增加明确兼容模式和直接替代关系；空兼容不再等于无限通用。三个试用 SKU 需补技术确认，不能把当前打开开关理解为兼容认证。
3. 提供统一候选/评估接口，前后端使用同一决定；保存时再次校验。
4. 增加与原订单行/受影响数量关联的单次限制、未履行重复申请检测、规则版本及理由快照。额度提交的并发保护要同步实施。
5. 建立按产品族审批过的质保适用配置，旧模板未经确认不自动继承到新产品。

验收：已知不兼容不能创建或执行；未知兼容能解释缺什么；停售原单仍可识别；非实物无补发路径；两个并发申请不能突破同一授权额度。试用开关迁移时逐项处理，禁止静默把所有空值变成“通用”。

### 第二期：覆盖套装、耗材及例外

增加购买时组件展开及证据、耗材单位/规格、数量累计台账、审批、换机链和客户同意记录。先人工核对批次并保存证据。处理部分授权、部分发出、撤回、退回及再次故障。

验收：源单已经拆件时不再次展开；取消未履行授权释放额度；已发出量保留；新旧 SKU 同时出现不重复算权益；正常耗尽与质量问题走不同路径。

### 第三期：接入实际履约

先核实马邦目标商品、库存预占、批次/效期、创建售后单和查单能力，再实现独立履约适配器。缺少的能力保留人工模式。增加 outbox、外部请求幂等、结果对账及超时恢复；不要先把四个只读 API 的连接改成自动写入。

验收：上游超时重试不重复下单；规则撤销/召回后阻止未执行请求；库存快照过期不宣称已预占；实际发出能对应授权行、商品、数量和外部凭据。

## 10. 必须覆盖的业务场景

| 场景 | 预期行为 |
| --- | --- |
| 美国版原机，候选欧洲版 | 以已确认电气/市场关系判断；不能只凭 device 类型放行 |
| 风嘴兼容关系为空 | 待配置，不视为所有设备通用 |
| 新品改补翻新机 | 需要明确允许的替代策略和客户同意/审批；保修衔接单独决定 |
| 停售原机改用后继型号 | 旧单仍能识别，只推荐已审核的有向关系 |
| 套装缺一个风嘴 | 依据购买时组成和缺件证据补组件，不默认送整套 |
| 原订单已包含组件行 | 保留套装与组件关联，不重复计算可服务数量 |
| 耗材新旧配方及颜色不同 | 兼容、效果和客户选择均需满足，不能当普通别名合并 |
| 一瓶与一盒、不同容量 | 使用明确单位换算和业务授权，不把数量 1 视为同量 |
| 两客服针对同一设备同时申请 | 原子额度检查和授权，避免重复承诺 |
| 换机后又故障 | 关联原资产和换机链，按新诉求评估，不机械终身拒绝 |
| 已授权后商品召回或批次过期 | 保留历史授权，阻止实际履约并进入处理流程 |
| 马邦 SKU 名称变化或新别名同步 | 不改写旧单快照，不自动转移许可、合并实物或生成替代关系 |

## 11. 需要业务及产品确认的事项

优先确认三项：型号/硬件兼容矩阵、各市场售后政策、单次及重复补发额度。之后再逐步确定套装历史版本、翻新替代和客户同意方式、耗材质量与正常消耗界限、批次及最低剩余效期、换机后的质保起止、先补后退条件、审批权限和成本门槛。

没有确定的值先保存为待配置并提示具体缺失项，不默认兼容、不默认保内、不默认一律允许，也不为展示完整而编造商品规格。
