# Udesk 有限 API 下的同步实施计划

日期：2026-10-16。状态：研究与拟实施方案；未修改应用逻辑、未注册源端回调、未调用租户数据 API。

## 决策

使用 Go 后台任务和 PostgreSQL 维护可重建的工单读取模型。交互查询不依赖全量源扫描；源 Udesk 继续拥有工单状态和内容。第一版即使没有增量查询或工单事件推送也能运行，按实际额度和同步耗时定义新鲜度。未来若验证出增量或事件能力，替换同步策略而不是重写页面。

这不是 PostgreSQL 原生 MATERIALIZED VIEW 的要求；普通表、受控写入与索引即可。也不把 RMA 草稿、快照和正式业务当可丢弃缓存。

## 研究证据

- [Udesk 列表与导出](https://www.udesk.cn/doc/apiv2/tickets/)：列表最多 100 条；导出按 filter_id 开始，每批最多 1,000 条，连续使用新 scroll_id，到空批结束。scroll_id 一分钟过期；不是持久增量游标。文档没有声明列表的更新时间区间、排序参数或导出快照隔离保证。
- [Udesk 调用限制](https://www.udesk.cn/doc/apiv2/intro/#_1)：默认 60 次/分钟；租户实际额度、按接口/账号/租户的计数范围需要验证。
- [Udesk Webhook](https://www.udesk.cn/doc/apiv2/webhook_v2/)：公开列出的客户、公司、IM 和客服组事件不包含通用 Ticket_update。通话触发器不能视为工单变更推送。搜索发现工单触发器通知第三方的二手线索，尚未证实租户可用能力。
- [Airbyte 增量前提](https://docs.airbyte.com/platform/connector-development/connector-builder-ui/incremental-sync)：既要有更新时间字段，也要能按该字段请求/过滤；仅在本地比较更新时间不减少源读取量。
- [Airbyte 可恢复全量](https://docs.airbyte.com/platform/connector-development/cdk-python/resumable-full-refresh-stream)：无增量时使用全量；断点恢复依赖分页稳定性。Udesk 过期 scroll 不可照搬长期恢复。
- [Microsoft 读取模型](https://learn.microsoft.com/en-us/azure/architecture/patterns/materialized-view)：预计算查询模型、明确陈旧窗口、可重建和原子发布。
- [Shopify Webhook 对账](https://shopify.dev/docs/apps/build/webhooks#implement-reconciliation-jobs)：事件可能漏送/乱序，仍应周期对账。此为通用经验，不代表 Udesk 提供同样契约。
- [AWS 超时和重试](https://aws.amazon.com/builders-library/timeouts-retries-and-backoff-with-jitter/)：限次、退避、抖动、重试预算，避免多层重试放大流量。

## 1. 能力核验与基线

先做有限的租户只读验证，不自动创建过滤器或回调：

1. 确认覆盖目标范围的过滤器，比较列表与导出的 ID 集合、可见范围、字段、自定义字段和返回数量。不仅比较 total。
2. 测量导出批次大小、耗时、错误和 scroll 过期行为；区分认证问题、能力不可用与瞬时错误。
3. 核验已有“最近更新”过滤器是否覆盖回复、转派、自定义字段更新；没有则保留周期全量方案。
4. 查明工单触发器“通知第三方”的租户能力、事件范围、认证和重试约定。公开通用 Webhook 不是工单事件证明。
5. 记录列表/详情 p50、p95 和每操作源请求数，并核实限流规则。

## 2. 当前边界内的数据模型

用后续版本 migration 扩展现有表，不修改已执行的 v1：

- support_access.tickets：增加类型化 subject/status/channel、created_at/updated_at/replied_at、数值工单号及索引；保留完整源内容。先按实际排序/查询建索引，自定义字段不全量展开成表。
- support_access 内新增筛选器快照和成员集合：租户、过滤器、执行身份、generation、成功时间；成员唯一键按 generation + ticket ID。
- integration 内增加持久同步任务：范围、去重键、租约、重试时间、运行版本、统计和错误；复用已有运行记录。
- configuration 增加经过限界校验的同步周期、过期阈值、已支持过滤器和请求预算。
- access_control 保持身份和授权权威；rma 保留自己的快照、草稿和业务，不由重建读取模型删除。

不预建通用 ETL 平台、消息总线或全公司的同步框架。

## 3. 后台同步

基础全量导出 + 按需单工单刷新；若能力核验通过，再增加近期更新过滤器或事件任务。

- 同租户同范围同一时间一个有效任务，多用户刷新合并；PG 租约协调跨进程，租约失效后旧 worker 不可发布结果。
- 网络请求不占用长事务。批次暂存、幂等写入；只有完整扫描成功才发布新筛选器 generation/完整范围状态。
- scroll 过期后重新开始该导出。保留已获取行用于去重与降低本地写入成本，不假装可从过期游标继续。
- 源 updated_at 已确认较旧的数据不得覆盖较新数据；相同时间但内容不同或版本缺失时采用保守冲突处理/单工单校验，不能当作可严格排序的版本号。
- 未出现在一个过滤器内，仅表示移出该集合。完整范围扫描也不直接等价于删除：标记待核验/不可见，对疑似消失工单定点核验，不破坏 RMA 历史。
- 指纹减少 PG 重复更新，不能减少源拉取成本。
- 元数据低频同步，与工单分开；手动强制同步有冷却和去重。

初始可配置候选：当前约数百张时完整校准 5 分钟；已验证的近期更新集合 1 分钟；元数据 30 分钟。均是待测参数，不是 SLA。无近期更新能力时不启用该任务；完整校准需始终存在。

限流按已核实维度执行，最初可保守限制整个集成账号总量。给交互请求保留容量，后台与重试不能耗尽额度；导出批次间隔同时须满足一分钟游标寿命。

请求预算约为：Σ ceil(每范围工单数 / 实际批次大小) / 同步周期 + 结束确认请求 + 详情/回复/附件校验 + 重试。重叠过滤器也有源读取成本。若扫描耗时超过目标周期，合并/跳过重复任务并暴露落后状态，不叠加任务。

## 4. 交互读取与权限

- 列表、搜索、筛选、排序、分页、导出统一由服务端执行。先应用租户、当前用户权限、筛选器集合、搜索，再排序分页；总数同范围。
- 对外保留一致分页 UI；服务端提供稳定 ID 次排序。大数据深翻页再用 keyset；刷新/版本变化时重置过期游标，避免承诺跨同步页面静态不变。
- 个人相对筛选器不能把管理员身份的结果冒充当前客服结果；未验证语义的筛选器明确不支持。
- 首次完整同步未成功显示初始化状态；同步中可读最后完整版本。返回范围成功时间、同步状态和过期信息；不把单张刷新时间当全集时间。
- 列表使用最近成功分配关系；普通客服超过允许过期阈值暂停列表敏感信息，管理员可在明确提示下查看旧索引。阈值在实施时配置并测试。
- 详情/回复/附件先做最新源权限校验，源不可用时不静默展示敏感缓存；本地账号停用/角色/组调整每请求即时生效。
- 同次详情与首屏回复由服务端共用一次详情校验；并发同工单源读取合并，但每个用户分别授权。跨请求权限缓存若引入，必须明确定义窗口，不默认为实时。
- 回复可持久缓存，但不能仅凭工单回复时间就假定历史回复不可编辑/删除。按需刷新和周期校准，不预取全部工单的全部对话。
- 附件继续验证归属；复用已授权内容引用，签名链接失效时重新解析。RMA 创建/提交单独刷新并保留快照。

## 5. 可选事件加速

仅在租户能力证实后实施：公网可达 HTTPS 回调（现有 192.168.1.61 私网地址不能直接作为 SaaS 可达端点）、认证、持久 inbox、去重、快速确认、合并工单更新任务。事件作为重新获取权威详情的提示，避免乱序 payload 覆盖新数据。周期校准始终保留。

## 6. 验收与提交顺序

1. 能力验证记录与索引 migration。
2. 后台导出同步、租约/限流/故障恢复及原子发布。
3. PG 列表/全局搜索/筛选/排序/计数/导出。
4. 同步状态 UI、设置项和中英翻译。
5. 详情/回复/附件请求复用。
6. 仅在验证后增加增量/事件支持。

每项独立提交；应用代码变动后重启两端并保持 LAN 服务。

验收：初始化后翻页/搜索/排序零 Udesk 请求；同范围并发刷新只一任务；失败不发布半份集合；多实例失去租约不可提交；旧版本不覆盖新版本；不同角色查询/计数/导出无越权；转派/源失败/权限停用策略正确；已有 RMA/设置/登录回归通过。以列表 API p95 < 500ms 为当前规模初始目标，实测后报告，不承诺未知规模。区分 last_success_age 和真实源变更延迟，非快照全量扫描不能报告一个精确 synced-through 水位。

## 扩展上限

本地查询可横向扩展，源变更发现速度仍受上游约束。若只有全量且额度固定，无法同时保证任意数据规模与秒级全量新鲜度。达到预算上限后，选择放宽新鲜度、验证缩小扫描范围，或向源供应商取得增量/事件/更高额度/受支持的数据导出；增加 Redis/Kafka 不能创造上游未提供的变化信息。
