# RMA 补发配置说明与完善范围

核对日期：2026-10-26（北京时间），5186 工作树。这里区分已实现、当前配置和待开发能力，不将设计文档视为上线功能。

## 当前配置分别控制什么

| 入口/配置 | 控制的问题 | 作用于谁 | 不能据此推断 |
| --- | --- | --- | --- |
| 商品：允许识别原订单商品 | 原单商品能否被确认用于 RMA | 原购买商品 | 不代表保内、可补发或客户归属已核实 |
| 商品：SKU 类型 | 区分整机、配件、待分类；按任务限制补发类型 | 原商品/补发商品 | 同为配件或整机不代表兼容或可替换 |
| 商品：质保类别 | 选择匹配质保政策的类别 | 受影响的原购买商品 | none 是未配置，不能一律解释为无需质保；不能凭此决定具体期限 |
| 商品：允许补发 | SKU 能否成为补发候选；创建/执行重新校验 | 目标补发商品 | 不授予免费权益、不证明兼容或有库存 |
| 商品：配置原因及版本 | 记录策略修改依据、审计与并发保护 | 本次配置变更 | 不是客服逐单申请原因 |
| 设置：质保规则 | 期限、适用类别/SKU/市场/平台、启用及生效日期计算 | 原购买商品及本次证据 | 当前通用模板不是已审批的全产品统一政策 |
| 售后配置：方案与任务 DAG | 采取什么处理、生成什么任务、先后依赖，是否需要质保 | 整张 RMA | 方案名称不等于实际已发货/退款；工单 RMA 目前只接受整机补发/配件补发 |
| 售后配置：任务类型 | 任务的物流方向、是否需要商品/数量/金额/凭据等 | 每个任务 | 内置行为受到保护；改名字不会接通外部执行 |
| 售后配置：审批规则 | 按任务、数量、金额、平台、根因等决定是否需要审批 | 每个任务 | 审批不是兼容性规则，不能证明质保资格 |
| 售后配置：根因 | 问题分类、可适用原 SKU；可参与审批条件 | 本次诉求 | 选择“设备故障”不是故障真实性证明 |
| 售后配置：平台 | 原单所属销售平台是否可用 | 原订单 | 不是收货国家、市场或物流路线 |
| 售后配置：自定义字段 | 收集 RMA/商品/任务/执行等额外资料，可设必填 | 指定表单范围 | 添加字段本身不会自动成为兼容、审批或履约规则 |
| 工单售后组成员/角色权限 | 谁能查看工单、创建、维护、审批、执行 | 操作者 | 权限许可不是商品/权益许可 |
| 马邦目录及库存同步 | 原商品事实、仓库数量快照、源商品是否仍存在 | 来源数据 | 仓库关联不等于可用库存；快照不等于预占 |

SN 注册是另一个独立能力。若在 RMA 中填写 SN，现有后端要求它已经登记且匹配所选原商品；暂时没有 SN 不应随便填写一个字符串。

## 一笔 RMA 的配置和证据链

1. 平台启用；操作者拥有相应权限并可访问该工单。
2. 查询并确认原订单及原商品。订单状态、编号及商品匹配通过不等于客户归属已经验证，客服仍需核实工单与原单关系。
3. 原商品允许识别；若方案要求质保，原商品有适用质保类别和唯一匹配的启用政策。
4. 选择适用方案、根因，填写描述、方案原因及交付证据。签收/激活日期来自独立依据，不用付款或发货时间冒充。
5. 目标补发商品已分类、允许补发且源商品仍存在；类型满足方案。
6. 当前后端检查方案/质保/数量格式/商品许可及版本，再保存 RMA、原单/商品/规则快照并生成任务。
7. 有审批要求时审批；实际执行由有权限的管理员记录。物流任务需要承运商和运单号；当前不会调用马邦创建订单、预占库存或发货接口。

以上能支持当前人工登记流程，但尚不代表兼容、重复申请、质量或实际履约已经具备完整控制。

## 完善分两类：可配置资料与待开发能力

### 已有功能内先整理

- 按实际售后政策审核原商品分类、质保类别、期限、起算依据及市场/平台范围；不为通过测试而全部设成整机或统一保内。
- 明确原购买商品与目标补发商品的不同，审核 allowOriginal/allowReship，不自动批量打开。
- 确定补发方案、根因、角色和审批门槛。使用现有任务级规则时注意它不是整张 RMA 的总成本或跨单累计额度。
- 审核内置旧模板，特别是打印头类别与实际 Halo/ColorBox 产品的关系，移除不适用的用户选项前先评估历史引用。
- 明确客服要收集什么证据，哪些执行凭据必须保存；不要把新建字段误当成新业务规则。

### 需要开发，不能靠现有设置补出来

| 优先级 | 能力 | 完善标准 |
| --- | --- | --- |
| 首先 | 统一身份映射和客户/订单关系确认 | 店铺/来源/有效期明确，无歧义；错订单不作为当前客户的补发依据 |
| 首先 | 兼容与替代关系及后端统一评估 | 未配置不是通用；原型号到目标型号的市场、版本和成色限制在创建/执行强制生效 |
| 首先 | 数量/次数/重复申请额度 | 关联订单行或设备，并发申请和跨工单累计不能突破授权 |
| 随套装业务上线 | 套装组成与历史版本 | 区分买整套、缺组件及上游已拆件，防止重复展开和计算 |
| 随耗材业务上线 | 耗材规格、单位、批次、效期、召回/冻结 | 兼容正确且实际批次可用；上游字段/接口先验证，缺失时人工核对留证 |
| 自动履约之前 | 履约请求、库存预占、外部查单与幂等对账 | 外部超时不重复下单；当前人工记录不冒充上游已履约 |
| 配置量增加之前 | 配置草稿、影响预览、发布与版本 | 业务可维护且知道改动影响；旧单依据不可被后来配置覆盖 |

详细模型、模块数据所有权及分期见 [售后商品与补发规则设计](after-sales-product-policy-design.md)。

## 局域网 HTTP 创建报错修复

局域网 `http://192.168.1.61:5186` 不属于浏览器安全上下文，现场观察到 `crypto.randomUUID` 不可用，`crypto.getRandomValues` 可用。旧前端在发送创建请求前生成幂等键时抛错；通知和新建质保规则也存在同一调用。

统一 ID 工具优先使用原生 randomUUID，否则用 getRandomValues 生成 UUID v4；不使用 Math.random。提交准备放在 try/finally 内，异常后释放提交锁。相同 payload 重试继续复用同一幂等键。此改动修复浏览器能力兼容，不跳过后端权限、质保、商品或数量校验。
